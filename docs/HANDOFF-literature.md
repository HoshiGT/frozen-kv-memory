# 文献调研交接

给接手做文献调研的人/模型。读完这份就能判断一篇论文跟我们相不相关。

---

## 一、这个项目在做什么

把 LLM 的长上下文 KV cache 变小，同时尽量不丢信息。最终形态是**两种记忆的混合**：

```
最近 1024 token   →  64 个学出来的"记忆槽"（抽象状态，7 MB）   要点、走向
更早的全部历史    →  原文 KV，offload 到内存，按需调回 512 条   精确细节
```

**关键约束：主干模型完全冻结**，只训练记忆槽本身（0.03M–3.67M 参数）。

指标：`recovery = (无上下文损失 − 本方法损失) / (无上下文损失 − 完整上下文损失)`，单位 nats。
1.0 = 与完整 KV cache 无异，0 = 等于没有上下文。**超过 1.0 是可能的**
（学出来的状态是为"预测下一段"优化的，原始 KV 不是）。

规模：Qwen3 0.6B / 1.7B / 4B，单张 8GB 笔记本显卡，全部本地。

## 二、已经得到的主要结论

按对文献检索的相关度排序：

1. **天花板由"精确回忆"构成**。把待预测的 token 按"答案能否从上下文复制"分组：
   从未出现过的 token 恢复率 **+231%**（抽象状态比完整原文 KV 还好用），
   出现过的只有 **+59%**，只出现过一次的只有 **+46%**。
   后者占 79.6% 的 token、携带 76% 的信息缺口。
   结论：理解可以压缩，一串数字不能，所以压缩有原理性上限。

2. **贡献可以分离**。固定检索到的 512 条原文 KV 不变，只换背后的东西：
   无状态 +46.1%、加训练好的抽象状态 +84.9%、换成随机状态 −40%、
   改用 oracle（已知答案的完美检索）+103.9%。
   即：检索贡献 46.1 点，压缩贡献 38.8 点，完美选择还能再加 19.0 点。

3. **冻结主干才测得准**。同配置下开 LoRA，`lower`（无上下文基线）从 3.951 降到 3.370，
   即微调让"没有上下文"这个基线好了 0.58 nats，分母缩小三分之一，
   recovery 从 +66% 变成 +8%——指标被污染了。
   **限定：此问题只对相对指标成立**，报绝对任务准确率的工作不受影响。

4. **三个杠杆都推不动天花板**：训练更久、模型从 0.6B 到 4B、预算从 64 槽到 128 槽，
   8 跳递归的数字全部停在 ~60%。

5. **滚动记忆不累积**。只压最近 512 token（+65.6%）比让状态滚过全部 8192（+61.5%）更好，
   滚动在稀释最近那段。有效窗口约等于一段。

6. **任务差异极大**。同一 checkpoint：真实对话 gap 1.269 nats，古腾堡小说 gap 仅 0.286。
   对连贯叙事而言长上下文本来就不值钱。

7. **方差很大**。同配置换随机种子重训，最难档位（16 槽）的 recovery 在 −8% 到 +83% 之间。
   任何只差几个点的结论都不可靠。

## 三、已经确认撞车的工作（不用再查，但可作为对比基准）

| 论文 | 与我们的关系 |
|---|---|
| SpeCache (arXiv 2503.16163) | KV offload 到 CPU + 预测下一步会 attend 哪些 KV 再预取。与我们的"推测式检索"高度重合 |
| Strong Drafts Need Compact Memories (arXiv 2608.30252, EMNLP 2026 Findings) | 压缩的远期记忆 + 精确的近期上下文。架构与我们高度重合（但用于 speculative decoding 的 draft 侧） |
| Self-Pruned KV Attention (arXiv 2605.14037) | 学一个 utility predictor 决定保留哪些 KV，backbone 联合微调 |
| Benchmarking KV-Cache Optimizations (arXiv 2607.05399) | 已系统研究"压缩效果随任务而变"，与上面第 6 条重合 |
| Compressive Transformer / RMT / LCIRC (2502.06139) | 递归压缩记忆，"有效窗口局限于近期"的现象已知，与第 5 条部分重合 |

## 四、需要回答的问题

**优先级最高的两个**（决定这个项目还剩不剩贡献）：

- **Q1**：有没有人把上下文压缩的性能损失**按 token 类型拆解**过？
  例如区分"该 token 在上下文中出现过、可直接复制"与"从未出现过"，
  或按 token 在上下文中的出现频次分组，分别统计恢复率。
  （对应上面结论 1）

- **Q2**：有没有人把"压缩"与"检索"的贡献**分离量化**过？
  例如固定检索结果只替换压缩状态、或用 oracle 确定检索的性能上界。
  （对应上面结论 2）

**其次**：

- **Q3**：有没有人指出过"微调 backbone 会抬高无上下文基线、从而夸大相对压缩指标"这个混淆？
  有没有人明确主张评测上下文压缩时应冻结 backbone？（对应结论 3）

- **Q4**（背景工作，最耗时但最不烧脑）：列出 2023–2026 年 KV cache 压缩/稀疏化/检索的主要工作，
  至少覆盖 H2O、SnapKV、PyramidKV、StreamingLLM、Quest、InfLLM、KIVI、
  Gist Tokens、ICAE、AutoCompressor、Compressive Transformer、RMT。
  每篇一行：**arXiv ID | 方法一句话 | 压缩比 | 评测指标（perplexity 还是任务准确率）|
  backbone 冻结还是微调 | 评测数据集**。

## 五、注意事项

1. **排除 `github.com/HoshiGT/frozen-kv-memory`** ——那是本项目自己的仓库，
   2026-09-21 才公开就被搜索引擎索引了，会以"已有工作"的面目出现在结果里。
   它不构成任何证据。

2. **必须给 arXiv ID 或可验证链接**。不确定的标注"存疑"，
   **不要编造论文**——编造的引用比没有结论更糟。

3. 找到相关工作是**好消息**，不是坏消息。目的是搞清楚这个项目还剩什么贡献，
   而不是证明它有贡献。如果 Q1、Q2 都已经有人做过，那就如实说。

4. 我们的指标是 perplexity/CE 类的相对量，很多工作报的是下游任务准确率。
   判断相关性时看**机制**，不要因为指标不同就跳过。
